## 1. 技术依赖齐备性（原生 ASR / 本地通知 / 本地存储·双端成熟度）

### 1.1 原生 ASR（F2）
| 平台 | 方案 | 离线能力 | 成熟度 | 关键依赖/约束 |
|------|------|---------|--------|--------------|
| iOS | `Speech`（`SFSpeechRecognizer` + `AVAudioEngine`） | iOS 13+ 支持 **on-device 识别**，但需用户**预先下载中文离线语言包**；否则回退联网识别（音频上传 Apple） | 高，官方一等公民 | `NSSpeechRecognitionUsageDescription` + 麦克风权限；on-device 非默认开启 |
| Android | `android.speech.SpeechRecognizer` | 多数设备**默认联网**（走 Google 语音识别）；离线需设备已装离线语言包 | 中，官方但碎片化 | 依赖 **Google App / GMS**；无 GMS 设备（部分国产 ROM、华为）**可能完全不可用**；`RECORD_AUDIO` 权限 |

**结论**：
- 双端均有官方 ASR，基础「持续听 + 实时转写」可行。
- **离线 ASR 双端都不是默认 Guaranteed**：iOS 需预装离线包，Android 多依赖联网 + GMS。这与「纯本地零网络」原则（架构 §1.4）及「无网络可用」（PRD R-U2）存在张力——ASR 联网回退会突破「纯本地」口径（见 §5.3）。
- **Android GMS 依赖是本土化高危项**：若目标市场含无 GMS 设备（华为等），`SpeechRecognizer` 可能整体不可用，F2 在这些设备直接退文字（R-X1）。需确认是否接受，或 v1.1 前是否需要第三方 ASR 兜底（F9 提前）。

### 1.2 本地通知 / 提醒（F3）
| 平台 | 方案 | 后台/被杀健壮性 | 成熟度 |
|------|------|----------------|--------|
| iOS | `UNUserNotificationCenter` + `UNCalendarNotificationTrigger` | 系统级调度，**App 被杀后仍按时触发**（pending 请求由系统持有） | 高 |
| Android | `WorkManager`（`OneTimeWorkRequest` + `initialDelay`）+ `NotificationManager` | 官方推荐的可靠后台调度；Doze 下可能延迟，优于裸 `AlarmManager` | 高 |

**结论**：双端本地通知方案成熟、选型正确；iOS 被杀不丢提醒，Android 用 WorkManager + 重启补偿可覆盖大部分场景。主要风险在**系统级拦截（DND/专注/低电量）**，属不可绕过项，需 PRD 文案与兜底策略（见 §5.2、§7）。

### 1.3 本地存储（F6）
| 平台 | 方案 | 成熟度 | 备注 |
|------|------|--------|------|
| iOS | Core Data（主）/ GRDB（备选） | 高 | 与 SwiftUI 深度集成；GRDB 为显式 SQL 备选 |
| Android | Room | 高 | 编译期 SQL 校验、Flow 集成好 |

**结论**：双端均为官方 SQLite 封装，事务、迁移、结构化查询齐备，单日数据量极小，**存储不是风险点**。架构预留 `schema version` 与 `updatedAt/syncState` 字段，为 v1.1 云同步留好扩展点，设计合理。

## 2. PRD 与架构一致性核查

### 2.1 功能清单对齐
- PRD v1：F1 / F2 / F3 / F4(P1) / F5 / F6 / F-perm(P0)；v1.1：F7 / F8 / F9。架构 §2、§4–§6 均覆盖，且 §0/§4.3 防蔓延声明一致。✅
- 架构未把 `F-perm` 列为独立模块，而是分散在 ASR（麦克风/语音识别授权）与通知（DND 绕过授权）两节。**无功能遗漏**，但建议架构补一张「权限清单与引导流程」小节，便于研发按 checklist 实现与测试验收（AC-21/AC-22）。

### 2.2 数据模型对齐（详见 §3）
- 实体 `Task / Reminder / Category / Tag` 与 PRD 字段需求基本对应；`RecurringTemplate / MakeupRecord` 仅 v1.1，已正确预留。
- **冲突点 A（存储损坏兜底）**：PRD R-X2 / AC-19 要求「尝试从备份恢复 → 失败则提示用户并保留可操作内存态、不崩溃」；架构 §3.1 写道「v1 可仅记日志」。二者口径不一致，需收敛（见 §6 一致性问题）。

### 2.3 接口对齐
- 架构定义 `TaskRepository / ASRController / ReminderScheduler` 三抽象，符合「接口先行」原则。✅
- **缺口 B（未来提醒查询）**：`ReminderScheduler.rescheduleAllPending()` 需枚举「未来未完成且含提醒的待办」，但 `TaskRepository` 接口（§7.2）仅暴露 `todayTasks()`，**缺少跨日/未来提醒查询方法**，重启补偿无法实现（见 §3.3）。

### 2.4 流程对齐
- 文字流、语音流、提醒流、循环流（v1.1）在 PRD §6 与架构 §4/§5 一致。✅
- **冲突点 C（拆分标点集）**：PRD R-E2 拆分信号含「，。！？；、**、换行**」；架构 §4.3 拆分规则仅列「。！？，；」，**缺「、」与「换行」**。需统一（见 §6）。

## 3. 数据模型充分性（逐需求核对）

### 3.1 PRD 字段需求覆盖核对
| PRD 所需字段/状态 | 架构 Task 字段 | 覆盖 |
|------------------|--------------|------|
| 内容 | `title` | ✅ |
| 所属日 | `date` | ✅ |
| 分类 | `categoryId`（默认「其他」） | ✅ |
| 优先级 高/中/低 | `priority`（默认中） | ✅ |
| 标签（多对多） | `tagIds` 关联表 | ✅ |
| 完成态 | `isDone` | ✅ |
| 完成时间（统计用） | `doneAt` | ✅（v1.1 用，v1 可暂不打满） |
| 主提醒时间 | `remindAt` | ✅ |
| 拖拽顺序 | `sortOrder` | ✅ |
| 来源追溯 | `source`（语音/文字/模板/补生成） | ✅ |
| 循环模板来源 | `templateId`（v1.1） | ✅ |
| 同步预留 | `updatedAt` / `syncState` | ✅ |
| 提醒触发点（提前/到点/重复） | `Reminder`（fireAt/type/repeatIndex/fired/cancelled） | ✅ |
| 重复开关 / 提前量可调 | **无独立字段** | ❌ 缺口（见 3.2） |

### 3.2 字段级缺口（需补，避免返工）
1. **提前量可调（leadMinutes）**：PRD §6.3 写明「可改提前量」，AC 含单条关重复，但 Task 仅有 `remindAt`，提前提醒由架构固定按 `T-10` 推导。若「提前量」按任务可调，需在 `Task` 增加 `leadMinutes`（默认 10），否则 F3「提前量可调」无法落地、且后期返工改表。
   - *建议*：v1 即便默认固定 10 分钟，也先把 `leadMinutes` 字段落库，避免 v1.1 迁移。
2. **重复次数可调（repeatCount）**：同理，若单条可改「最多 3 次」，建议 `Task` 增加 `repeatCount`（默认 3）或在 `Reminder` 由行数推导。当前靠「是否存在重复行」隐式表达，可调时需显式字段。

### 3.3 接口级缺口
3. **未来/跨日提醒查询**：`ReminderScheduler.rescheduleAllPending()` 要补偿重启后丢失的 pending，必须能列出「`remindAt` 在未来且未完成」的待办（可能跨自然日，见 §5.4）。`TaskRepository` 现有 `todayTasks()` 不足以支撑，需补充如 `tasksWithPendingReminders()` 或 `tasksUntil(date:)`。
   - *风险*：若不补，重启补偿只能覆盖「今天」的提醒，跨 0 点的重复提醒（如 23:50 设定、T+30 到次日 00:20）会丢失。

## 4. 兼容性与实现风险

### 4.1 iOS / Android 差异
| 差异点 | iOS | Android | 风险与建议 |
|--------|-----|---------|-----------|
| 提醒调度模型 | 一次性预排 T-10/T/T+10/T+20/T+30 共 5 条；完成即批量取消 | 各触发点起独立 Work，触发时**实时检查完成态** | 行为等价，但「完成态判定时机」不同：iOS 是「排程时假设未完成」，Android 是「触发时查」。需统一验收口径，确保「完成即不再响」一致 |
| DND / 专注拦截 | **无法绕过**系统专注模式 | `setBypassDnd(true)` 需 `ACCESS_NOTIFICATION_POLICY` 用户授权 | iOS 只能 PRD 文案引导；Android 需新增授权引导。DND 下响铃不可控，统一走「App 内待完成列表兜底」 |
| ASR 离线 | on-device 需预装包 | 多数联网、离线需语言包、无 GMS 可能不可用 | 见 §1.1 / §5.3 |
| 领域逻辑双实现 | Swift | Kotlin | 架构 §1.3/§4.3 称「双端共用同一算法与阈值」，但 Swift/Kotlin 是两套代码，**存在漂移风险**（见 4.4） |

### 4.2 后台限制
- iOS：被杀后系统仍持有 pending 通知，可靠；但**语音录制必须在前台**，后台即停（语音为交互式录入，可接受）。
- Android：Doze 下 WorkManager 可能延迟；架构已选 WorkManager + 重启补偿，方向正确。需 QA 覆盖「低电量/Doze/被杀」三场景（PRD AC-10 / R-X3）。
- **结论**：后台限制不改变方案可行性，但需把「被杀/Doze 下的提醒可靠性」列为 QA 重点，并以 PRD R-S4/R-X3 的 App 内兜底为验收底线。

### 4.3 ASR 离线（重点风险）
- 「纯本地零网络」（架构 §1.4）与「ASR 联网回退」冲突：iOS 未装离线包时回退联网会将音频发往 Apple；Android 默认联网发往 Google。
- 这同时冲击**隐私口径**：PRD §9 称「语音在设备端经系统 ASR 转写，不上传账号」——严格说音频是「上传到系统厂商」而非「账号」，但绝非「纯本地」。
- **需产品/架构拍板**（见 §7 未决点 4）：是「强制 on-device 仅离线（失败即退文字，牺牲语音覆盖率）」，还是「允许联网识别（语音可用但非纯本地，需重写隐私文案）」。该决策直接影响 F2 在大量设备上的可用率与合规文案。

### 4.4 自动拆分误切（重点风险）
- 架构拆分配顿阈值 800ms–1.2s、句末标点、手动「落一条」三信号。阈值**硬编码有返工风险**。
- PRD/架构均同意「v1 支持手动合并/拆分纠正」（F2 + US-6 + AC-5），方向正确，但该纠正的持久化需数据层支持（已覆盖，`isDone/sortOrder` 等足以表达）。
- **双端拆分逻辑漂移风险**：同一算法用 Swift/Kotlin 各写一遍，阈值若分散在两端易不一致。建议将阈值/标点集集中在**双端共享的配置常量**（或共享规格文档 / KMM 共享模块），从第一天即参数化，避免后期对齐返工。

### 4.5 其他实现风险
- **跨自然日提醒语义**：任务归属「今天」（`date`），但 T+30 可能进入次日；日切 0:00 时 App 未打开，列表清空为「新的一天」，而昨日任务的提醒仍 pending（架构扫未来 7 天会保留）。需明确：跨日提醒是否继续响、日切时未处理提醒如何归类（是「错过的提醒」还是「延续」）。属产品语义待定（见 §7）。
- **通知交互 Action**：架构 §5.2 提到 iOS 通知 `category` 带「标记完成 / 推迟 10 分钟」Action，但 PRD 仅明确「标记完成取消后续」（R-E7），「推迟」Action 未在 PRD 出现。需确认是否 v1 实现「推迟」交互。
- **文档笔误（不影响落地，建议清）**：架构 §1.3 领域层标注「纯 Dart/Swift/Kotlin」，但 §2 明确选 SwiftUI + Compose（原生），Dart/Flutter 与本方案矛盾，应为「Swift/Kotlin」，建议修订以免误导。

## 5. 范围与优先级建议

### 5.1 v1 实现顺序建议（仅顺序，非排期）
| 阶段 | 内容 | 理由 |
|------|------|------|
| ① | 双端骨架 + 数据层（Task/Category/Tag + Repository）+ F1 文字新增 + F5 完成/编辑/删除/拖拽 + F6 持久化 | 零外部依赖、风险最低，先跑通「记录→完成」主闭环，验证 X/Y 进度 |
| ② | F-perm 权限引导（麦克风/通知/DND 授权）+ F3 提醒（含重启补偿） | 提醒是核心差异点，跨平台差异大，宜早暴露；权限是 F2/F3 的准入前提 |
| ③ | F2 语音输入（持续听 + 自动拆分 + 联网/授权失败降级） | **最高风险**（ASR 离线/ GMS / 误切），放最后攻坚，避免阻塞基础闭环 |
| ④ | F4 分类/优先级/标签（P1） | 与核心闭环解耦，可平行推进；P1 须随 v1 上线 |

> 与架构 §10 落地建议基本一致（架构把 F4 放最后，本评审因 F4=P1 建议可平行，不冲突）。

### 5.2 可后置（v1.1，确认不进 v1）
- F7 历史统计、F8 周模板循环、F9 第三方 ASR：架构已预留 `RecurringTemplate / MakeupRecord`、`templateId / source`、抽象 `ASRController`，返工风险低，按 PRD 防蔓延声明后置即可。

### 5.3 返工风险研判
| 风险项 | 是否会导致返工 | 缓解 |
|--------|--------------|------|
| `leadMinutes` / `repeatCount` 字段缺失 | **会**（F3 提前量可调实现时改表） | v1 建表即加字段，默认 10/3 |
| `tasksWithPendingReminders()` 接口缺失 | **会**（重启补偿做不全） | 数据层先补查询方法 |
| 拆分阈值硬编码 | 中（后期双端对齐返工） | 阈值/标点集首日参数化、双端共享 |
| 循环/统计实体已预留 | 否 | 维持现状 |
| 存储损坏兜底口径冲突（R-X2 vs 仅记日志） | 会（验收争议） | 评审会先定 v1 做到哪一层（见 §6/§7） |

## 7. 待产品 / 架构进一步澄清的未决点（不拍板）

> 以下事项研发**不自行决定**，需对应负责人在开工前确认。

1. **提醒默认策略最终值**：提前 10 分 + 到点 + 每 10 分重复最多 3 次，是否采纳？（PRD §13-1 / 架构 §5.1 已按此默认，但标注待确认）
2. **提前量 / 重复次数是否按任务可调**：若可调，数据模型需加 `leadMinutes` / `repeatCount`（见 §3.2）。请产品明确可调范围。
3. **分类预设集合与标签策略**：预设「工作/生活/学习/其他」是否合适？标签是否开放自由录入、是否有数量/格式上限？
4. **ASR 离线 vs 联网回退策略（关键）**：强制 on-device 仅离线（失败退文字），还是允许联网识别？直接决定 F2 设备覆盖率与隐私文案（见 §5.3/§6-D）。
5. **隐私文案与合规**：零登录 + 本地存储 + ASR（可能联网）声明是否需法务/合规过审？尤其第 4 点确定后文案需同步。
6. **上架渠道与开发者账号**：iOS / 安卓走哪、何种账号？影响上架周期（纯本地零登录已降低账号依赖，但 ASR 联网回退可能触发 App Store 隐私声明）。
7. **待办文本长度上限**：超长截断或提示阈值（PRD 建议 500 字），需定具体值以落地输入框与存储。
8. **自动拆分停顿阈值默认值**：800ms–1.2s 是否合适？建议双端参数化并预留可调（见 §4.4）。
9. **Android GMS 依赖处置**：目标市场是否含无 GMS 设备？若含，F2 在这些设备是否接受直接退文字，还是需提前引入第三方 ASR（F9 前移）？
10. **跨自然日提醒语义**：任务归属「今天」但提醒可能跨 0 点；日切时未处理/未达提醒如何归类与处置（延续 / 计入「错过的提醒」）？
11. **通知交互 Action 范围**：v1 是否实现「标记完成 / 推迟 10 分钟」通知按钮？PRD 仅明确「标记完成」，「推迟」需确认。
12. **DND 绕过授权流程**：Android `ACCESS_NOTIFICATION_POLICY`（bypass DnD）是否在 v1 引导授权？iOS 无法绕过，文案如何引导用户到专注模式白名单？
13. **指标目标基线**：北极星 / 留存 / 触达等目标值（灰度后定，PRD 已标注待确认）。
14. **存储损坏兜底层级（v1）**：完整 R-X2 恢复 vs 简化（仅不崩溃 + 日志），需产品定级以对齐 AC-19（见 §6-A）。
15. **v1 是否完全不露 v1.1 入口**：PRD 默认不露 UI，请确认架构「仅扩展点」与产品预期一致。
