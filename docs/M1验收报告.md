## ② 逐条 AC 判定与证据

### AC-1（F1/R-E3）非空文字提交 → 新增「进行中」待办 + 输入框清空
**判定：通过（静态）**
- iOS：`TodayTaskViewModel.addFromInput()` 先 `trimmingCharacters` 后 `guard !raw.isEmpty` 拦截空内容（`LocalTaskRepository.swift:41-42`），`repository.add(task)` 新增（`LocalTaskRepository.swift:56`），成功后 `inputText = ""`（`TodayTaskViewModel.swift:57`）；UI 提交入口 `TodayView.swift:57-65`（TextField onCommit + 加号按钮）。
- Android：`TodayViewModel.addFromInput()` `raw.trim()` 后 `if (raw.isEmpty()) return`（`TodayViewModel.kt:55-56`），`repository.add`（`TodayViewModel.kt:66`），成功后 `_inputText.value = ""`（`TodayViewModel.kt:68`）；UI `TodayScreen.kt:74-87`。
- 新增默认 `isDone=false`（进行中）：`TaskDTO.makeNew`（`TaskDTO.swift:40-50`）、`Task.makeNew`（`Task.kt:40-55`）。

### AC-14（F5/R-S1）勾选完成 → 置底 + 完成态 + 进度 X+1
**判定：通过（静态）**
- 「置底」由查询排序保证：iOS `todayTasks()` `ORDER BY isDone ASC, sortOrder ASC`（`LocalTaskRepository.swift:23-26`）；Android `TaskDao.todayTasks` `ORDER BY is_done ASC, sort_order ASC`（`TaskDao.kt:19-24`）。
- 「完成态」：iOS `TaskRowView.swift:18-29` 勾选图标 + `strikethrough` + 灰色；Android `TaskItem.kt:54-61,76-79` 绿色对勾 + `LineThrough`。
- 「进度 X+1」：`doneCount` 实时统计 `isDone` 数量，标记完成时 `markDone`（`LocalTaskRepository.swift:81-92` / `LocalTaskRepository.kt:33-35`）→ `reload()` 重算，UI 显示「完成 X / 共 Y」（iOS `TodayView.swift:24`、Android `TodayScreen.kt:46-49`）。

### AC-15（F5/R-U3）进度实时「完成 X / 共 Y」，Y 含进行中+已完成
**判定：通过（静态）**
- iOS：`doneCount`/`totalCount`（`TodayTaskViewModel.swift:17-18`）——`totalCount = tasks.count`（含已完成）。
- Android：`doneCount`/`totalCount`（`TodayViewModel.kt:34-35`）——`totalCount = _tasks.value.size`（含已完成）。
- 每次写操作后均 `reload()` 刷新（`TodayTaskViewModel.swift` 各方法末；`TodayViewModel.kt` `.onSuccess { reload() }`），进度实时。

### AC-16（F5）拖拽排序后顺序持久化
**判定：通过（静态）**
- iOS：VM `reorder(from:to:)` 计算新 id 顺序并调 `repository.reorder(ids:)`（`TodayTaskViewModel.swift:108-119`）；UI `List.onMove`（`TodayView.swift:49-52`）；Repository `reorder` 将每条 `sortOrder=index` 并单事务提交（`LocalTaskRepository.swift:105-117`）。
- Android：VM `reorder(from,to)`（`TodayViewModel.kt:112-120`）；UI 提供上移/下移按钮（`TaskItem.kt:111-116`、`TodayScreen.kt:63-68`）；DAO `reorder` `@Transaction` 批量 `updateSortOrder`（`TaskDao.kt:47-53`），Repository 注入新 `sortOrder`（`LocalTaskRepository.kt:42-46`）。
- 持久化：写入后均 `save()`/`@Update`，重启由 `todayTasks` 按 `sortOrder` 还原（见 AC-17）。**顺序持久化逻辑静态成立；拖拽手感需真机确认。**

### AC-17（F6/R-U1）杀进程/重启 → 当日列表完整恢复
**判定：代码路径通过 / 需真机验证**
- 列表从库加载（非内存）：iOS `reload()`→`repository.todayTasks()`（`TodayTaskViewModel.swift:30-36`）；Android `reload()`→`repository.todayTasks()`（`TodayViewModel.kt:42-48`）。
- 全部写操作落库：iOS `add/update/markDone/delete` 均 `context.save()`（`LocalTaskRepository.swift:53,77,90,101`）、`reorder` 单事务 `save()`（`:115`）；Android 各 DAO 写操作由 Room 原子提交（`TaskDao.kt`）。
- 单事务提交保证杀进程不丢（设计规格 §1.7）。
- **静态可证逻辑完整；「重启后完整恢复（含完成态/顺序/分类/提醒）」的端到端行为需真机验证**：杀进程后冷启动，检查列表、完成态、排序、预设分类、已存 `remindAt` 是否全部回归。

### AC-18（F6/R-U2）无网络 → 记录/查看/完成/编辑全部可用
**判定：通过（静态）**
- 全栈无任何网络依赖：Repository 仅依赖 Core Data / Room 本地存储；ViewModel 无网络调用；`syncState` 字段仅预埋（`"local"`），M1 不消费（设计规格 §0）。无网络分支、无远程写入路径。**纯本地实现，无网可用静态成立。**

### AC-19（F6/R-X2）本地存储损坏 → 不崩溃 + 记日志 + 提示数据可能受损
**判定：部分通过（代码路径齐备 / 需真机验证）**
- iOS：捕获点 `PersistenceController.init` 对 `loadStoresSafely` 抛错 `try/catch`（`PersistenceController.swift:34-41`），首启种子失败亦捕获（`:46-51`），绝不外抛到 UI；`rebuildEmptyStore` 删除损坏 SQLite 主文件及 `-wal/-shm` 并重建空库（`:73-97`）；`logDBError` 写入 `Application Support/logs/db_error.log` 且含 `timestamp/event/dbPath/errorType/message/action` 字段、仅本地不联网（`:100-129`）；重建后 `didRebuildOnCorruption=true` → `DailyPlanApp.swift:13-18` 弹一次性提示「本地数据可能已损坏」（`:24-28`）。
- Android：`DatabaseProvider.get` 对 `openHelper.writableDatabase` 抛错 `try/catch` → `DBErrorLogger.log` + `deleteDatabase` + 重建（`:17-32`），极端磁盘满 `runCatching` 不抛（`:28`）；`DBErrorLogger.log` 写入 `filesDir/logs/db_error.log`，字段齐备（`:17-37`）；重建后由 `DailyPlanApplication.onCreate` 的 `seedPresetCategoriesIfNeeded()` 重新播种预设分类（`DailyPlanApplication.kt:16`）。
- **符合 P0-3 方案 B（不崩溃 + 日志 + 不强制恢复）。**
- **遗留**：iOS/Android 重建后是否真正「保留可操作内存态并提示」的端到端行为需真机注入损坏库验证（见 §④ 一般-1：日志缺少 `event=migration_failed` 在重建路径中的精确对齐，详见缺陷清单）。

### AC-26（F5/R-E10）取消完成 → X-1、回进行中；提醒排程恢复
**判定：部分通过（数据层满足；提醒恢复属 F3）**
- 取消完成数据层：iOS `toggleDone` 当 `task.isDone` 时置 `isDone=false, doneAt=nil` 并 `repository.update`（`:65-72`）；Android `toggleDone` `repository.update(task.copy(isDone=false, doneAt=null))`（`:79-81`）。`reload()` 后 X-1、回到进行中（排序 `isDone ASC`）。
- **提醒排程恢复**（AC-26 后半句「其提醒排程恢复并按原计划触发」）属 F3 业务：M1 已持久化 `remindAt/leadMinutes/repeatCount` 且「取消完成」`update` 完整保留这些字段（`LocalTaskRepository.update` `LocalTaskRepository.swift:64-76` / `LocalTaskRepository.kt:28-31`），但**实际排程逻辑 F3 未实现，无法在 M1 验证**。属预期范围外，记录为跟进项（§⑥）。

### AC-27（F1/R-U4,R-U5）跨日/时区归属与绝对时间不漂移
**判定：部分通过（① 数据层满足；②③ 依赖 F3）**
- ① 待办按「创建自然日」归属当日清单：双端 `date` 写入均为设备本地时区 `yyyy-MM-dd`，`TimeZone.current` / `TimeZone.getDefault()`（`DateFormatter.todayDateString` `TaskDTO.swift:57-63`；`todayDateString` `Task.kt:60-64`），`todayTasks` 按 `date == today` 过滤（`LocalTaskRepository.swift:19-21` / `TaskDao.kt:19-24`）。**数据层满足。**
- ② 提醒跨越自然日仍按时触发并归入当天 → 依赖 F3 通知排程，M1 未实现。
- ③ 切换时区已设绝对提醒时间不变：`remindAt` 以设备本地绝对 `Date` 持久化（`Converters` `Converters.kt:11-13`；Core Data `Date` 属性），读写不做时区换算，**存储层满足「不漂移」**；但「按本地时区展示/触发」的端到端行为依赖 F3，需真机验证。

### AC-29（F1/R-X5）超长文本 ≥500 字 → 截断至 500 并提示
**判定：通过（静态，双端提示行为略有差异）**
- iOS：add 路径 `raw.count > 500` → `String(raw.prefix(500))` + `errorMessage = "内容超过 500 字，已截断。"`（`TodayTaskViewModel.swift:44-51`）；编辑路径 `editTitle` 同样截断（`:86-87`）。
- Android：add 路径 `raw.length > 500` → `raw.take(500)` + 提示（`:58-61`）；编辑路径 `editTitle`（`:93-94`）。
- ⚠️ 差异：Android 截断提示 2.5s 后自动消失（`TodayScreen.kt:37-42`）；iOS 提示常驻直到下一次错误覆盖（`TodayView.swift:31-36`，无自动清除）。功能正确，体验不一致（见 §④ 建议-1）。
- 截断单位差异：iOS `String.count`（字素簇）vs Android `String.length`（UTF-16 码元），纯 CJK 等价，混 emoji 时边界不同（§④ 建议-2）。

## ③ P0 决策落实验证（P0-2 / P0-3 / P0-4）

### P0-2 提醒默认策略（leadMinutes 默认 10 / repeatCount 默认 3，单条可覆盖）
**判定：落实（静态）**
- 默认值双端一致：iOS `TaskDTO.makeNew` `leadMinutes:10, repeatCount:3`（`TaskDTO.swift:43-44`）+ Core Data 属性默认 `10`/`3`（`PersistenceController.swift:172-173`）；Android `Task.makeNew` `leadMinutes=10, repeatCount=3`（`Task.kt:49-50`）+ `@Entity` `defaultValue="10"/"3"`（`TaskEntity.kt:21-22`）。
- 单条可覆盖：Repository `update` 全量写入 `leadMinutes/repeatCount`（iOS `LocalTaskRepository.swift:71-72` / 安卓 `LocalTaskRepository.kt:30`），`add` 接受调用方传入值。
- 注意：P0-2 的**排程语义（提前 10min + 到点 + 每 10min 重复最多 3 次）属 F3**，M1 仅存字段与默认，逻辑验证留待 M2/F3（符合设计规格 §0「仅存字段」）。

### P0-3 存储损坏兜底（v1 = 方案 B：不崩溃 + 日志，不强制恢复）
**判定：落实（静态，端到端需真机）**
- 见 AC-19 证据。双端均实现：DB 打开/迁移 try-catch + 本地日志（格式符合规格 §10.2）+ 删损坏库 + 重建空库 + 首启种子重播 + UI 一次性提示，且异常绝不外抛。
- 与 PRD/R-X2/AC-19 口径一致（v1 不强制恢复）。

### P0-4 语音拆分规则（标点 `{。！？；}` + 长停顿 1200ms，不含「、」与换行）
**判定：结构落实（静态）；F2 未实现故未消费**
- 双端均实现「从同源配置解析、禁止硬编码」：`shared/asr_split_config.json`（`splitPunctuation:["。","！","？","；"]`, `splitPauseThresholdMs:1200`, `includeEnumerationComma:false`, `includeNewline:false`）。
- iOS `ASRSplitConfig.loadFromBundle()`（`ASRSplitConfig.swift`）从包内 `asr_split_config.json` 解析；Android `ASRSplitConfig.load(context)`（`ASRSplitConfig.kt`）从 `assets/asr_split_config.json` 解析。
- 配置值与规格 §8.3 完全一致，双端同源。
- 该配置为 F2 消费，M1 仅定义结构与解析能力，**拆分算法本身不在 M1**，故仅验证「结构+解析就绪」，不验证切分效果（F2）。

## ④ 缺陷清单（按严重级）

### 🔴 阻塞（Blocker）
- 无。M1 数据层与 F1/F5/F6 核心功能在静态审查下无阻塞级缺陷；全部 7 个 Repository 方法双端齐备且语义与设计规格一致。

### 🟠 严重（Critical）
- 无。

### 🟡 一般（Major / Minor）
- **一般-1（Android 损坏重建后日志事件对齐）**：`DatabaseProvider.get` 在 `open_failed` 后 `deleteDatabase` 再 `build` 并打 `corrupt_detected`（`DatabaseProvider.kt:22-25`），但重建空库后**未重新触发首启种子失败的捕获**（种子在 `DailyPlanApplication.onCreate` 异步执行，`AppContainer:30-34` 用裸 `CoroutineScope(Dispatchers.IO)` 未绑定生命周期）。极端情况下若重建后种子写入仍失败，仅记日志、无二次提示，但**不崩溃**，符合 P0-3 口径；建议将种子纳入 `get()` 的捕获链以保证重建后必有可用预设分类。属稳健性改进，非阻断。
- **一般-2（iOS 重建后未重新播种的对称性）**：iOS `PersistenceController.init` 在 `loadStoresSafely` 抛错后先 `rebuildEmptyStore` 再 `seedPresetCategoriesIfNeeded`（`PersistenceController.swift:43-51`），顺序正确、会重新播种；但种子失败仅记 `migration_failed` 日志（`PersistenceController.swift:49`），提示文案为「打开失败」态，UI 提示文案与日志事件语义不完全对齐。建议日志事件名与 UI 提示映射更精确。
- **一般-3（AC-17/AC-19 端到端未经真机）**：所有「重启恢复」「损坏恢复」均为代码路径静态成立，沙箱无法运行，未做运行时验证。需在真机/模拟器补测（见 §⑤ 验证方法）。

### 🔵 建议（Suggestion）
- **建议-1（截断提示一致性）**：iOS 截断提示常驻（`TodayView.swift:31-36`），Android 2.5s 自动消失（`TodayScreen.kt:37-42`）。建议双端统一为短暂自动消失，避免提示长期占位。
- **建议-2（500 字计数口径一致性）**：iOS 用字素簇 `String.count`，Android 用 UTF-16 `length`。纯中文等价；含 emoji/复杂字符时截断边界不同。建议双端统一按「字符（Unicode 标量/码元）」口径并在规格中固化，避免跨端 500 字判定漂移（PRD AC-29 的「字」定义建议明确）。
- **建议-3（Android 拖拽交互）**：当前为「上移/下移」按钮（`TaskItem.kt:111-116`），非连续手指拖拽；设计规格 §5.1 言及「拖拽」，建议 F4 阶段补 `LazyColumn` 原生拖拽手势以贴合 AC-16「拖拽」表述（iOS 已用 `List.onMove` 原生拖拽）。
- **建议-4（errorMessage 清空策略）**：iOS `errorMessage` 在 addFromInput 截断后仍保留，且无 `clearError` 调用；Android 有 `clearError`。建议 iOS 也增加超时/交互后清除，避免提示残留。

## ⑤ 结论

**M1 是否达到进入下一里程碑（M2 / F3 提醒）的条件：建议「有条件通过 / 可进入 M2」，但须先完成真机补测。**

- **通过项（静态）**：AC-1、AC-14、AC-15、AC-16、AC-18、AC-29 逻辑完整且双端一致；Repository 7 方法（含 `tasksWithPendingReminders` 语义 = 未完成 + 有 `remindAt` + `remindAt ∈ [now, until]`，双端 SQL/谓词与规格 §5.3 一致）齐备；P0-2/P0-3/P0-4 决策均已在数据层落实；X/Y 进度计算正确；持久化写入路径（add/markDone/update/delete/reorder）均落库且单事务提交。
- **部分通过（需 F3 或真机补全）**：AC-17（重启恢复，代码路径完整，需真机端到端）、AC-19（损坏兜底，代码路径完整，需真机注入损坏库）、AC-26（取消完成数据层满足，提醒排程恢复属 F3）、AC-27（① 数据层满足；②③ 触发/展示属 F3）。
- **无阻塞/严重缺陷**，仅有稳健性改进（一般-1/2）与体验一致性建议（建议-1~4）。

**遗留风险**：
1. AC-17/AC-19 的端到端运行时行为未经真机验证（沙箱限制），是进入 M2 前必须补齐的验收闭环。
2. F3 提醒排程（AC-7/8/9/11/26 后半/27②③）依赖本 M1 已落库的 `remindAt/leadMinutes/repeatCount` 与 `tasksWithPendingReminders` 接口——M1 已为其冻结数据结构，进入 M2/F3 时**数据层零返工**，但 F3 业务正确性与跨日/时区触发仍待 F3 阶段验证。
3. 500 字计数口径（建议-2）与截断提示一致性（建议-1）虽不影响功能，建议进入 F4 前在规格中固化，避免后续跨端漂移。
