## 1. D3 / AC-10「错过的提醒」区

### 1.1 检测机制：「应响未响」判定

> 目标（PRD R-X3 / AC-10）：杀进程 / 系统未调度导致提醒未达时，用户下次打开 App 在首页「错过的提醒」区补列，标记「提醒未达」。M2 验收 D3 已确认该区在 M2 刻意未做，检测能力（权限回调）已就绪，范围归入 M4。

**判定原则（简单可靠，无需额外触发日志表）**：

- M2 的 `rescheduleAllPending` 在 App 启动/进入前台时扫描 `tasksWithPendingReminders(now, now+7天)` 得到「**未来待响**」任务（补偿重启/跨日）。
- 「**错过项 = 应响未响**」= `remindAt < now` **且** `isDone == false` **且** 该任务在「今日」展示口径下仍可见（见 §3 与下式）。
- 不引入 `Reminder.fired`/触发日志等额外表；依赖「计划触发时刻已过 + 未完成」这一可确定性推导，规避双端触发日志漂移。

**与 S5 展示日统一（关键）**：一条任务的「展示日」`displayDay(task)` 由 §3 定义。只有当 `displayDay(task) == 今日` 时，才进入首页任何区块。由此「错过的提醒」区今日集合定义为：

```
FUNCTION missedReminderTasks(today, now) -> [Task]:
    RETURN all tasks WHERE
        isDone == false
        AND remindAt != nil
        AND remindAt < now                       // 计划触发时刻已过期
        AND displayDay(task) == today            // 仅归今日展示（见 §3）
    ORDER BY remindAt ASC
```

> 说明：
> - `remindAt < now` 已隐含「应响未响」。若 App 在提醒时刻处于前台且系统已展示，该任务因未完成仍会被列入——这符合 PRD 口径「提醒未达 = 到点后未收到系统展示回调，且仍在错过的提醒区」（§10 数据口径）：我们**不区分**「其实响过但用户忽略」与「真未响」，统一标记「提醒未达」，提示用户回头确认。简单可靠、无平台差异。
> - 仅纳入 `displayDay == 今日`：避免把数天前未完成的历史待办永久塞入首页（噪声）。跨 0 点任务按触发日展示（§3），故其「错过」只在其触发日当天出现。
> - 与 `tasksWithPendingReminders` 互补：前者是「未来待响」，本区是「已过期待响未完」。两者共同构成首页提醒兜底。

## 2. D4 / AC-20 首页常驻提示

### 2.1 检测机制（复用 M2 已就绪回调）

> M2 验收 §② 确认：iOS `center.authorizationStatus`、Android `NotificationManagerCompat.areNotificationsEnabled()` 检测能力已具备，仅缺首页常驻 UI。本 M4 补 UI 横幅 + 深链。

- **通知权限被关**：
  - iOS：`UNUserNotificationCenter.current().getNotificationSettings { $0.authorizationStatus != .authorized }`。注：`.provisional`/`.ephemeral` 视为「可能不达」，同样显示提示；`.denied`/`notDetermined` 显示。
  - Android：`NotificationManagerCompat.from(ctx).areNotificationsEnabled() == false`。
- **DND / 勿扰拦截**（PRD R-S4 仅要求「通知被禁」回调，本 M4 增强覆盖 DND 提示，与 M2 §4.5 一致）：
  - iOS：**无可靠公开 API 检测 Focus/勿扰**，不强制检测；以「权限 + 文案引导」兜底（架构 §5.2 边界）。
  - Android（API ≥ 23）：`NotificationManager.currentInterruptionFilter`，当为 `INTERRUPTION_FILTER_NONE`（或仅 `INTERRUPTION_FILTER_ALARMS`/`PRIORITY`）且 App 未获「绕过勿扰」时，视为 DND 拦截风险。
- **显示条件（仅当有权限风险时）**：`showBanner = notifDisabled || dndActive`。无风险则不渲染，零打扰。

## 3. S5 跨日提醒列表归类

### 3.1 语义（已拍板，M2 验收 §⑦ #5）

- 提醒**按 `remindAt` 绝对时间触发**（M2 已实现，不变）。
- 当 `remindAt` 跨 0 点（即 `remindAt` 所属自然日 ≠ 任务 `date`），该任务在**触发日**显示为「进行中」——即首页「当日列表」的**归属展示日**取 `remindAt` 所属日（仅对跨 0 点任务）；普通任务仍按 `date`。
- **明确：不改动 `date` 存储字段**，仅展示层按 `remindAt` 重归类跨 0 点任务。
- 例：任务 `date = 2026-07-24`，`remindAt = 2026-07-25 07:30` → 该任务在 7/25 首页「进行中」列表出现（而非仅在 7/24）；7/24 当日列表不含它（除非其本身也在 7/24 进行中）。

### 3.3 首页「当日列表」分组（双端对照伪代码）

```
FUNCTION buildTodaySections(today, now) -> TodayViewSections:
    tasks = repository.todayTasks()              // M1：返回 date == today 的当日任务
    // 跨 0 点任务（remindAt 所属日 == today 但 date != today）需额外并入：
    crossDay = repository.tasksByDisplayDay(today) // 见下；或内存从全量未完成过滤

    all = (tasks + crossDay).dedupe(by: id)
    // 拆分三个区块
    missed    = all.filter { !$0.isDone && $0.remindAt < now && displayDay($0) == today }  // D3 区
    inProgress= all.filter { !$0.isDone && displayDay($0) == today && !missed.contains($0) }
    done      = all.filter {  $0.isDone && displayDay($0) == today }
    RETURN TodayViewSections(missed: missed, inProgress: inProgress, done: done)
```

> 跨 0 点任务的取数：为不改动 `todayTasks()`（按 `date` 过滤），建议新增只读查询（同 §1.2 精神，不新增字段）：

```sql
-- 取「展示日 == 某日」的全部未完成任务（含跨 0 点项）：
-- 展示日 = (remindAt 所属日) 当 remindAt 存在且 ≠ date，否则 date
SELECT * FROM task
WHERE is_done = 0
  AND (
        (remind_at IS NOT NULL AND date(remind_at, 'localtime') = :day AND date(remind_at,'localtime') <> date)
        OR date = :day
      );
```

- iOS（Core Data 谓词等价）：`NSPredicate(format: "isDone == NO AND ( (remindAt != nil AND %@ == remindAtDay AND remindAtDay != date) OR date == %@ )", today, today)`，其中 `remindAtDay` 为基于 `remindAt` 的本地日字符串（可用 fetch 时计算或存储冗余列——**本 M4 不新增列**，由内存/SQLite `date()` 函数计算）。
- 该查询仅用于「当日列表」构建，不影响 `date` 存储；完成态置底、排序沿用 M1（进行中在上、已完成置底、同组 `sortOrder` 升序）。

### 3.4 边界与对齐

- **时区**：`localDayString` 一律设备本地时区（R-U5），切换时区不重写 `remindAt`，仅展示日随本地时区解释（跨日边界随本地时区移动，符合 M2 §5.4）。
- **已完成跨 0 点任务**：同样按 `displayDay` 归入触发日「已完成」区，保持归类一致。
- **与 M2 §2.5 兜底的衔接**：跨 0 点任务的提醒触发仍由 `rescheduleAllPending` 覆盖（绝对时刻），本 §3 仅解决「列表里它出现在哪一天」。
- **验收**：AC-27②「设提醒 T 跨越自然日，到点仍触发并归入当天进行中展示」由本 §3 闭环（M2 验收当时标注「待产品确认」，现已拍板）。

### 4.2 合并/拆分 UI（AC-5）

> M3 §7 已冻结领域层 `TaskMergeSplitUseCase.merge(_:)` / `split(_:at:)`，并复用 M1 `update/add/delete` 持久化。M3 验收 D6/R-4 确认**双端缺 UI 入口**；本 M4 补 UI，领域逻辑直接复用，不重写。

**交互方案（双端对照）**：

| 维度 | iOS（SwiftUI） | Android（Jetpack Compose） |
|------|----------------|----------------------------|
| 触发 | 待办行 `.contextMenu { }` 或 `onLongPressGesture` 弹出操作 | 行 `combinedClickable(onLongClick=)` 弹 `DropdownMenu` / `ModalBottomSheet` |
| 菜单项 | 「合并到上一条」「从此处拆分」 | 同左 |
| 合并（合并到上一条） | 选中 task → 取列表中**相邻上一条**（sortOrder 紧邻、同展示日）作为参数与当前条 `merge([上一条, 当前条])` | 同左 |
| 拆分（从此处拆分） | 长按行 → 弹轻量编辑框，用户在 `title` 中移动光标选定断点 `index`（或默认按首个 `splitPunctuation` 标点断） → `split(task, at: index)` | 同左；编辑框用 `TextField` + 选区/光标位置 |
| 即时更新 | `merge/split` 走 M3 用例 → M1 `update/add/delete` 落库 → `@FetchRequest` 自动刷新 | 同左，`Flow` 自动刷新 |
| 持久化 | 经 M3 §7 已定义调用 `repository.update/add/delete`，**重启保持**（AC-5） | 同左 |
| 提醒联动 | 合并后提醒随主条、拆分前段带走 `remindAt`；改动后调 `ReminderScheduler.schedule/cancel`（复用 M2 §6） | 同左 |

**合并相邻规则（沿用 M3 §7.2）**：
- 保留参与合并各条的**最早 `date`、最前 `sortOrder`**；`title` 用「、」连接；`remindAt` 取合并中首个有提醒者；`isDone` 取「全完成才完成」；`updatedAt` 刷新。
- 「上一条」判定：当前任务在「当日列表」中的紧邻前序（按 `sortOrder`/展示顺序），且同 `displayDay`（§3）。

**拆分规则（沿用 M3 §7.2）**：
- 在第 `index` 处断开；断点若为 `splitPunctuation` 中标点，标点归属前段并丢弃（同 M3 §5.3）；两段 `source` 不变（`.voice`/`.text` 保留）；两段 `date` 相同、`sortOrder` 邻接；前段带走 `remindAt`。

**合并/拆分权限与边界**：
- 至少两条相邻才可「合并到上一条」（首条不可合并到上一条）。
- 拆分段为空（index 越界/空段）时忽略（R-X4 精神，不生成空条）。
