## ② 双端逐项核实结果

### 2.1 数据模型（不重定义 M1，仅扩展）— ✅ 双端通过（静态）

- iOS：`Priority`（`Enums.swift:8`）沿用 M1 String rawValue；`TaskDTO.makeNew`（`TaskDTO.swift:26`）默认 `categoryId = CategorySeed.otherId`、`priority = .default`（medium）；未新增任何 Task 列。
- Android：`Priority`（`Enums.kt:7`）沿用 `raw` + `from(raw) ?: MEDIUM`；`Task.makeNew`（`Task.kt:33`）默认 `categoryId = CategorySeed.OTHER_ID`、`priority = Priority.MEDIUM`；`TaskMappers.kt:18` 读取时 `Priority.from(priority)` 对 null/未知默认 **MEDIUM**（AC-30② 读取路径可靠）。
- 结论：严格复用 M1 `Category/Tag/Priority/TaskTagCrossRef`，零数据层返工。

### 2.2 Repository 筛选方法 — Android ✅ / iOS ⚠️（含编译阻断缺陷）

**方法签名（双端协议）全部对齐规格 §3.2**：`filteredTasks`(组合 AND)、`tasksByCategory/Priority/Tags`(单维便捷)、`suggestTags`(前缀联想)、`tags(forTaskId:)/tagsForTask`(读)、`setTags`(整体替换)。

- **Android（`LocalTaskRepository.kt` + `TaskDao.kt`）— ✅ 实现完整且逻辑正确**
  - `filteredTasks`：SQL `tasksByDateCategoryPriority` 处理「分类含其他=nil」(`category_id = :cat OR (:cat = :otherId AND category_id IS NULL)`)、优先级可空；标签 AND 与 `untaggedOnly` 在内存层用 `TaskFilter.matches`（`tagIds.all { it in taskTagIds }`）判定（规格 §3.4 推荐路径）。
  - `suggestTags`：`TagNormalizer.normalize` 前缀 → `LIKE :norm || '%'`，命中已归一 name。
  - `tagsForTask`：JOIN `task_tag` 读取；`setTags`：`@Transaction` 先 `DELETE` 后批量 `INSERT`（整体替换，规格 §2.4）。
  - `taskTagIds()`：批量读 `task_tag` 归并为 `taskId→Set<TagId>`，供内存筛选。
- **iOS（`LocalTaskRepository.swift`）— ⚠️ 逻辑正确，但文件无法编译（见缺陷 D1）**
  - 6 个 M5 方法（`tasksByCategory`/`tasksByPriority`/`tasksByTags`/`suggestTags`/`tags(forTaskId:)`/`setTags`）的**实现逻辑本身正确**：
    - `filteredTasks` 谓词含「筛选其他含 nil」(`categoryId == %@ OR categoryId == nil`)、标签 AND 用 `SUBQUERY(tags,$t,$t.id IN %@).@count == %d`、仅无标签用 `tags.@count == 0` ✅
    - `suggestTags`：`TagNormalizer.normalize` 前缀 → `BEGINSWITH` ✅
    - `tags(forTaskId:)`：读取 `task.tags` 关系 ✅
    - `setTags`：`task.tags = Set<Tag>()` 先清空后写（级联删除关联行）✅
  - **但是**：这些方法被写在 `struct LocalTaskRepository` 大括号**之外**（struct 未闭合），导致协议 `TaskRepository` 要求的方法未实现、`extension Task` 被错误嵌套进 struct、且方法引用的 `context` 无作用域 → **编译失败**（详见缺陷清单 D1）。
  - 修复为单行（补 `}`），逻辑无需改动。

### 2.3 标签归一去重（AC-30③ / R-O1）— ✅ 双端逻辑通过（静态）；归一边界需单测

- 双端均**复用 M1 `TagRepository.addOrReuse(normalizedName:)`** 命中同一 `Tag` 行天然去重，无另起炉灶。
- iOS `TagNormalizer.normalize`（`TagRepository.swift:47`）：`trim → applyingTransform(.fullwidthToHalfwidth) → lowercase`。规格 §5.1 声明该 transform 已含 U+3000，无需改。
- Android `TagNormalizer.normalize`（`TagNormalizer.kt:9`）：显式含 `c == '　' -> ' '`（U+3000→空格）分支 + `0xFF01..0xFF5E` 全角→半角，与规格 §5.1 补全建议**完全一致**。
- AC-30③ 三例静态推演：`Work`/` work `/`Ｗｏｒｋ` 经归一（trim→全角转半角→小写）均得 `work`，`addOrReuse("work")` 命中同一行 → 库内仅一条 `work` 标签；联想 `wo`/`ＷＯ` 因前缀先归一均命中。逻辑成立。
- 诚实标注：U+3000 与全角→半角的**运行时**等价性（尤其 iOS `.fullwidthToHalfwidth` 对 U+3000 的实际映射）未编译/运行验证，建议补一条单测锁定。

## ③ 缺陷清单

### D1 ［iOS］`LocalTaskRepository.swift` 结构体缺少闭合大括号（编译阻断）— 严重级：高 / Critical — ✅ 已修复

- **现象**：6 个 M5 方法（`tasksByCategory`/`tasksByPriority`/`tasksByTags`/`suggestTags`/`tags(forTaskId:)`/`setTags`）写在 `struct LocalTaskRepository` 大括号**之外**；`struct` 起始于 line 8、第 6 个方法 `setTags` 止于 line 234，但 `extension Task` 出现在 line 237 且未被 struct 关闭所包住。
- **量化证据**（Python 括号平衡脚本）：文件末尾大括号净深度 = **1**（未闭合 1 个 `{`）；line 237 `extension Task` 处括号深度 = **2**（被错误嵌套进 struct 内）。
- **后果**：
  1. `extension Task` 被解析为 struct 内部声明 → 编译错误；
  2. 即使忽略上一点，这 6 个方法若视作顶层自由函数，其引用的 `context`（struct 私有属性）无作用域 → 编译错误；
  3. 协议 `TaskRepository` 要求的 6 个方法未实现于 `LocalTaskRepository` → 协议一致性不成立。
- **定位**：`ios/DailyPlan/Repositories/LocalTaskRepository.swift`，line 234（`setTags` 结束）与 line 236（注释）之间。
- **修复（一行）**：在 `setTags` 方法之后、`// Task.fetchRequest() 便捷` 注释之前，补一个 `}`，使 struct 正确闭合；6 个方法即纳入 struct，协议一致性成立，文件可编译。
- **影响范围**：仅 iOS。逻辑本身已正确，修复后无需改动业务代码。**iOS 在修复前无法通过编译，M5 iOS 验收需先修复此缺陷。**
- **✅ 修复记录（协调者 #D1-fix）**：已在 `setTags` 方法之后、`// Task.fetchRequest()` 注释之前补入 struct 闭合 `}`（原 line 234 后）。修复后括号平衡脚本：open=63 / close=63 / 净深度=0；`extension Task` 现位于 struct 外（line 239，顶层，符合 M1 `CategoryRepository`/`TagRepository` 约定）；6 个 M5 方法（line 146~236）均在 struct 内；iOS 全项目 `.swift` 括号体检无不平衡。**D1 已闭环，iOS 现可编译。**

> 未发现其他缺陷。Android 实现完整、逻辑自洽；iOS 其余 M5 代码（协议、ViewModel、UI、归一器、默认值）静态均正确，唯一阻断项为 D1。

## ④ 结论

- **Android M5（F4）**：数据模型 / Repository / 归一去重 / UI / 默认值 五项静态核实**全部通过**，无缺陷。建议：可进入 **Stage 5 闭环**；仍建议补单测锁定 AC-30③ 归一边界与组合筛选 AND 语义（属「需真机/单测验证」项，非缺陷）。
- **iOS M5（F4）**：数据模型 / 协议 / ViewModel / UI / 归一去重 / 默认值 静态正确；原 D1 编译阻断缺陷（缺失 struct 闭合括号）**已由协调者单行修复并复验（括号平衡 63/63、全项目体检通过）**。iOS 现已可编译并进入 Stage 5 闭环；建议补单测验证归一边界与 AND 语义。
- **整体判定**：M5 F4 在「设计 + 实现意图」层面已达成规格 §7 与 AC-12/13/30①②③④、R-O1/R-O2 全部要求；唯一实质阻碍是 iOS D1 一处结构性编译缺陷（一行修复）。
