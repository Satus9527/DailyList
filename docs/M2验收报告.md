## ② 逐条 AC 判定与证据

### AC-7（F3/R-E4,R-E5）设时间 T（默认 leadMinutes=10）→ T-10min 与 T 各收到通知
- **判定：部分通过（逻辑成立，端到端需真机验证）**
- **证据**：
  - iOS `ReminderScheduler.buildTriggerPoints`：`leadMinutes>0` 生成 `__lead`（T−lead），`pts.append` 生成 `__at`（T）（`ReminderScheduler.swift:74-89`）。默认 `leadMinutes=10` 来自 `TaskDTO`/`Task` 模型默认。
  - Android 同算法（`WorkManagerReminderScheduler.kt:31-50`）。
  - `schedule` 用 `UNCalendarNotificationTrigger` / `setInitialDelay` 登记绝对时刻。
- **保留**：实际推送/展示需真机；Android 在 `now∈(T−L,T)` 区间重排时会重触发已过期的提前点（见缺陷 D2），可能影响本 AC 的"提前点只在该时刻响一次"。

### AC-8（F3/R-E6）到点未完成 → 每 10min 重复，最多 3 次（repeatCount 默认 3，可关闭）
- **判定：部分通过（逻辑成立，需真机；iOS 当 repeatCount>3 受 D1 影响）**
- **证据**：双端 `buildTriggerPoints` 在 `repeatCount>0` 时生成 `T+i×10min`（i=1..R）（`ReminderScheduler.swift:82-87` / `WorkManagerReminderScheduler.kt:41-48`），间隔严格 10 分钟（规格 §1.4）。
- **保留**：iOS 完成取消对 `R>3` 不彻底（D1）；重复点实际触发与 Doze/专注拦截需真机。

### AC-9（F3/R-E7）标记完成 → 后续提醒取消
- **判定：部分通过（主路径成立，iOS 在 repeatCount=4/5 下违反本 AC，需真机）**
- **证据（双端主路径一致）**：
  - App 内：`toggleDone` 标记完成后调 `scheduler.cancel`（iOS `TodayTaskViewModel.swift:87-89`；Android `TodayViewModel.kt:90-92`）。
  - 通知 Action：「标记完成」→ iOS `completeTask`（markDone+cancel，`ReminderScheduler.swift:185-189,274-276`）；Android `ReminderActionReceiver` → markDone + cancel（`ReminderActionReceiver.kt:32-35`）。
  - Android 额外兜底：Worker 触发时查 `isDone` 不发（`ReminderWorker.kt:31-35`，规格 §2.5）。iOS 因系统限制无此能力，靠"完成即 cancel + 幂等 Action + 列表兜底"（规格 §2.5，已记录平台边界）。
- **缺陷**：iOS `cancel(for:)` 仅枚举 `__rep{1..3}`（`repeatUpperBound=3`，`ReminderScheduler.swift:63,145-154`），但 UI 允许 `repeatCount=5`（见 §④）。当单条 `repeatCount=4/5` 时，完成 `cancel` 残留 `__rep{4,5}`，仍会在设定时刻触发，**违反 AC-9**。Android 因 `cancelAllWorkByTag` 全量移除无此问题。

### AC-10（F3/R-X3）杀进程致通知未达 → 重开后在"错过的提醒"区可见该条标记"提醒未达"
- **判定：不通过（M2 未实现，已明确延后）**
- **证据**：双端均无"错过的提醒"区块。iOS README 明确："首页「错过的提醒」区…仅留 requestAuthorizationIfNeeded 打点，UI 区…尚未实现（属 F-perm/首页增强，建议后续里程碑补齐）"（`ios/README.md:114-115`）。Android `TodayScreen.kt` / `TaskItem.kt` 亦无此区。当前仅以"普通待办列表"兜底。
- **范围说明**：M2 交付清单（设计规格 §9）未列本 AC 的 UI；属刻意未做，但 PRD 将其列为 F3 验收项，建议产品确认是否纳入 M2 或明确移至 M3（见 §⑦）。

### AC-11（F3）单条关闭重复（repeatCount=0）→ 仅保留提前+到点，不再重复
- **判定：通过（逻辑成立，需真机验证联动）**
- **证据**：`buildTriggerPoints` 以 `if repeatCount>0` 守卫（iOS `ReminderScheduler.swift:82`；Android `WorkManagerReminderScheduler.kt:41`）。UI 关闭开关即 `rc=0`（iOS `ReminderSettingView.swift:42,116`；Android `ReminderSettingSheet.kt:67,181`）。

### AC-20（F-perm/R-S4）通知被禁检测 → 首页常驻"提醒可能不送达"提示
- **判定：不通过（检测能力具备，首页常驻提示 UI 未实现）**
- **证据**：检测回调已具备——iOS `center.authorizationStatus`（`ReminderScheduler.swift:124-132,226-239`）；Android `NotificationManagerCompat.areNotificationsEnabled()` 在 `showReminder` 内用于决定是否展示（`ReminderNotificationHelper.kt:53`）。但**无任何首页常驻提示 Banner**（`TodayView.swift` / `TodayScreen.kt` 均无）。
- **范围说明**：同 AC-10，属 F-perm/首页增强，M2 未实现 UI，检测机制已就绪。

### AC-26（F5/R-E10）取消完成 → 进度 X-1；若有未触发提醒，排程恢复并按原计划触发
- **判定：通过（逻辑成立，端到端需真机）**
- **证据**：`toggleDone` 取消完成分支：`isDone=false,doneAt=nil` → `update` → 若 `remindAt` 在未来则 `schedule` 恢复（iOS `TodayTaskViewModel.swift:75-84`；Android `TodayViewModel.kt:83-88`）。数据层 `remindAt/leadMinutes/repeatCount` 在 `update` 中完整保留（iOS `LocalTaskRepository.swift:57-79`；Android `LocalTaskRepository.kt:28-31`）。M1 验收 §③ 已确认数据层满足，M2 补齐调用链。

### AC-27②（F1/R-U4）设提醒 T 跨越自然日，到点仍触发并归入"当天进行中"
- **判定：部分通过**
- **证据（触发正确）**：`tasksWithPendingReminders` 仅按 `remindAt∈[now,until]` 过滤、**不过滤 `date`**（iOS `LocalTaskRepository.swift:32-45`；Android `TaskDao.kt:60-68`），故跨日 `remindAt` 仍被 `rescheduleAllPending` 纳入并触发。
- **待确认（产品语义）**：任务 `date` 归属创建当日，但跨 0 点的提醒触发时，列表仅在 `date` 当日展示（`todayTasks` 按 `date` 过滤）。跨日提醒"归入触发日进行中"的归类语义待产品拍板（评审结论 #9 / 需拍板 #10）。

### AC-27③（F1/R-U5）切换时区后已设绝对提醒时间不变（不漂移），仅展示随本地时区解释
- **判定：通过（数据层+触发逻辑满足，端到端需真机）**
- **证据**：`remindAt` 以设备本地绝对 `Date` 持久化，读写不做时区换算（iOS `Date` 属性；Android `Converters`）。`UNCalendarNotificationTrigger(dateMatching:)` / `setInitialDelay` 均基于绝对时刻计算（规格 §1/§5），天然符合。

### AC-28（F3/R-E11）提醒改期 T→T'：旧触发点取消、仅 T' 生效，不重复通知
- **判定：通过（逻辑成立，端到端需真机）**
- **证据**：`saveReminder` → `scheduler.schedule`，而 `schedule` 内含 `cancel` 先清旧点再按新 T 重建（iOS `ReminderScheduler.swift:97-121,199-209` + `TodayTaskViewModel.swift:140-158`；Android `WorkManagerReminderScheduler.kt:52-74` + `TodayViewModel.kt:144-160`）。`remindAt=nil` 或已过期则 `cancel`（`TodayTaskViewModel.swift:149-153` / `TodayViewModel.kt:155-156`）。

## ③ 触发点 / 补偿 / DND 专项核对

### 3.1 触发点生成规则（双端一致，规格 §2）
- **leadMinutes>0 才生成提前点**：✅ 双端 `if leadMinutes>0`（iOS `ReminderScheduler.swift:77`；Android `WorkManagerReminderScheduler.kt:34`）。
- **总是生成到点**：✅ `pts.append(__at)`（iOS `:81`；Android `:40`）。
- **repeatCount>0 才生成 R 个重复点（T+10…T+R×10）**：✅ `for i in 1...repeatCount`（iOS `:82-87`；Android `:41-48`）。
- **L=0 / R=0 边界**：✅ L=0 → 不进 `if`，无 `__lead`；R=0 → 不进 `if`，无 `__rep*`（UI 关闭开关→`lm=0/rc=0`，`ReminderSettingView.swift:115-116` / `ReminderSettingSheet.kt:180-181`）。
- **默认集合 T−10/T/T+10/T+20/T+30（5 点）**：✅ 当 L=10,R=3 成立。
- **重复间隔严格 10 分钟**：✅ `i×10×60`（规格 §1.4）。

### 3.2 完成时取消剩余提醒（markDone 路径调 cancel）
- **iOS**：`TodayTaskViewModel.toggleDone` → `scheduler.cancel`（`TodayTaskViewModel.swift:89`）；通知 Action → `completeTask` → `repository.markDone + cancel`（`ReminderScheduler.swift:185-189`）。✅ 接线正确（但见 D1 上限缺陷）。
- **Android**：`TodayViewModel.toggleDone` → `reminderScheduler.cancel`（`TodayViewModel.kt:92`）；`ReminderActionReceiver` → `scheduler.cancel`（`ReminderActionReceiver.kt:34`）。✅ 接线正确；且 Worker 触发时 `isDone` 查（`ReminderWorker.kt:31-35`）作兜底。

### 3.3 重启 / 跨日补偿（rescheduleAllPending 扫描未来 7 天）
- **扫描语义**：`tasksWithPendingReminders(now, now+7天)`（iOS `ReminderScheduler.swift:192-204`；Android `WorkManagerReminderScheduler.kt:99-112`；`REMINDER_SCAN_HORIZON_DAYS=7`，`ReminderContract.kt:27` / `ReminderScheduler.swift:60`）。✅ 与规格 §5 一致。
- **触发时机（双端）**：
  - iOS：冷/热启动 `DailyPlanApp.init`（`DailyPlanApp.swift:30`）+ 进入前台 `scenePhase==.active`（`DailyPlanApp.swift:43-47`）。✅
  - Android：Application 启动 `DailyPlanApplication.onCreate` 仅建渠道（未在 Application 直接调 reschedule，由首屏 `onResume` 触发）；`MainActivity.onResume` → `viewModel.rescheduleReminders()`（`MainActivity.kt:57-60`）；`BootReceiver` → `rescheduleAllPending`（`BootReceiver.kt:23`）。✅
- **幂等重建**：`schedule` 内含 `cancel`，重复调用安全（规格 §5）。✅
- **WorkManager 重启韧性**：Android `OneTimeWorkRequest` 由 WorkManager 持久化，重启后自动重排；`BootReceiver` 作二次修复（规格 §4.4）。✅ iOS 依赖系统通知中心保留 + 启动重建。✅

### 3.4 iOS 通知 Action（标记完成 / 推迟 10 分）回调
- **注册**：`registerCategory` 注册 `UNNotificationCategory`（`REMINDER_CATEGORY`）含两 Action（`ReminderScheduler.swift:209-221`）。✅
- **回调**：`didReceive` 按 `actionIdentifier` 分发 `completeTask` / `snooze`（`ReminderScheduler.swift:265-282`）；并设 `willPresent` 前台也展示（`ReminderScheduler.swift:258-262`）。✅
- **snooze 幂等**：先 `removePendingNotificationRequests(__snooze)` 再建新（`ReminderScheduler.swift:157-169`）。✅

### 3.5 Android DND（setBypassDnd + 权限引导）
- **setBypassDnd**：`ReminderNotificationHelper.showReminder` 仅当 `DndPolicyHelper.isBypassDndGranted` 时 `builder.setBypassDnd(true)`（`ReminderNotificationHelper.kt:78-80`）。✅
- **权限检测/引导**：`DndPolicyHelper.isBypassDndGranted`（`DndPolicyHelper.kt:18-22`）；`maybeRequestDndPolicy` 用 `SharedPreferences` 去重后跳 `ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS`（`DndPolicyHelper.kt:36-42`）；`MainActivity.onResume` 调用（`MainActivity.kt:62`）。✅ `AndroidManifest.xml` 声明 `ACCESS_NOTIFICATION_POLICY`（`AndroidManifest.xml:8`）。✅

## ⑤ 缺陷清单

### 阻塞（Blocker）：无

### 严重（Critical）
- **D1｜iOS 完成取消对高序号重复点不彻底（违反 AC-9）**
  - 位置：iOS `ReminderScheduler.swift:63`（`private let repeatUpperBound = 3`）、`:145-154`（`cancel` 仅枚举 `__rep{1..3}`）；UI `ReminderSettingView.swift:29`（`repeatOptions = [1,2,3,5]`）。
  - 现象：单条 `repeatCount=4/5` 时，`markDone`→`cancel` 仅移除 `__rep{1..3}`，残留 `__rep{4,5}` 仍触发，任务完成后仍响，违反 AC-9 / R-E7。
  - 修复：将 `repeatUpperBound` 提到 ≥ UI 最大值（建议 5 或更高安全常量如 10）；同步修订设计规格 §3.1 `REPEAT_MAX=3` 口径。Android 无此问题（tag 全量取消）。

### 一般（Major）
- **D2｜Android `schedule` 缺过期触发点守卫，补偿时重触发已过期提前点**
  - 位置：Android `WorkManagerReminderScheduler.schedule`（`WorkManagerReminderScheduler.kt:52-74`），无「跳过已过期点」判断（对照 iOS `ReminderScheduler.swift:107` `guard pt.fireAt > Date()`）。
  - 现象：`rescheduleAllPending` 在 `now∈(T−L, T)`（如 App 被杀后于提前点之后、到点之前重新打开）被调用时，已过期的「提前点」以 `delay=0` 立即触发，产生重复/迟到的提前提醒。
  - 修复：补 `if (pt.fireAt.time <= now) continue`，与 iOS 对齐。
- **D3｜AC-10 首页「错过的提醒」区未实现（双端）**
  - 现象：无"通知未达"检测与补列 UI，仅以普通待办列表兜底。iOS README 已标注为刻意未做（`ios/README.md:114`）。
  - 处置：建议产品确认是否纳入 M2 或明确延后至 M3（见 §⑦）。
- **D4｜AC-20 首页「提醒可能不送达」常驻提示 UI 未实现（双端）**
  - 现象：检测能力（authorizationStatus / areNotificationsEnabled）已具备，但首页无常驻提示 Banner。
  - 处置：同 D3，建议产品确认范围。

### 建议（Suggestion）
- **S1**：统一"repeatCount 上限"口径（规格 §3.1 `REPEAT_MAX=3` vs UI 上限 5），避免双端实现分歧（关联 D1）。
- **S2**：iOS 通知 Action「标记完成」使用 `.authenticationRequired`（`ReminderScheduler.swift:210-212`），锁屏需先解锁再标记；建议产品确认是否符合预期（一般可接受）。
- **S3**：埋点仅留调用点注释（规格 §6.5），未接通上报；建议 M3 前确定埋点方案（reminder_set/trigger/complete 等）。
- **S4**：DND/专注模式"引导文案"已写入代码注释/Helper，但 App 内「设置页/首次提醒说明」引导 UI 未实现（仅 Android `onResume` 跳系统设置，iOS 仅日志）；建议补引导 UI。
- **S5**：跨日提醒列表归类语义（评审结论 #9 / 需拍板 #10）待产品拍板——`date` 归属当日但 `remindAt` 跨 0 点，是否继续响并归入触发日"进行中"（当前通知会响，但列表仅在 `date` 当日展示）。
